# Per-project Linear pick-up — 2026-09-30

Version: lin 0.36.4; implementation: code-internal. As of this change:

Settings → Connections supplies the preferred Linear connection, selecting named CLI accounts explicitly and retaining credentials with lin. Existing assignment, search, issue and project reads remain read-only; optional assignment import creates projects. The older Advanced linear configuration uses a direct GraphQL client only when no lin connection supersedes it. Both paths run at startup, every five minutes and through manual sync, without writes to Linear.

Project Config gains an optional Linear card after Team settings using existing styles. The owner selects a connection/account, team or project, status names and assignee rules (anyone, unassigned, me or chosen users), and enables pick-up. Unlinked projects remain untouched. Core owns records and validation; the optional adapter depends on core. Source links appear in the task panel and board card, whose anchor is raised above the card overlay and tested.

Supplied research identified GraphQL IssueFilter team.id, project.id, state.name.in, assignee.id.in, assignee.null and assignee.isMe filters and cursor pagination. Offline lin 0.36.4 help confirmed team list/states, project list, user list and api query with JSON variables and explicit workspace selection. No live schema request was made. Queries are constants; only variables change. Reference: https://linear.app/developers/graphql.

Metadata pages select only id, identifier, title and URL, ten issues per page. Each sweep buffers at most five pages, then reads descriptions separately for new issues before any imports. Stored descriptions are bounded to 8KiB with a truncation marker. Individual responses exceeding the runner's 128KiB cap produce an explicit omission marker and retain the source link, allowing later issues to proceed. Authentication, transport, malformed data and GraphQL failures still abort the buffered import. Descriptions enter the team's brief as untrusted external context, never acceptance criteria or authority to override instructions.

At most 50 tasks are created per project per sweep, with normal brief/playbook readiness and PM triage. Task creation, source provenance and globally unique issue-ID receipts share a transaction. Restart and concurrent sweeps cannot create duplicates or orphan receipts. Receipts survive unlink/relink, connection/account changes and stopped/finished tasks. Snapshot receipts skip known nodes before context reads and core calls; atomic checks still guard races. Unchanged error/cursor updates and duplicate imports do not rewrite state. Imported-task activity reaches the assistant and appears as Asked in dashboard Steps.

A version-guarded scan cursor resumes after the last completely processed page, resetting at the end of each pass. Only failure of the first issue-page read starting from a saved cursor resets that cursor; readiness, discovery, later-page and description failures retain progress. No growing receipt exclusion filter is sent. A crash before cursor persistence repeats deduplicated reads; a partly processed page is repeated rather than skipped. Rule edits, disabling pick-up and unlinking invalidate stale reads and reset progress. A resumed sweep spends its first page on the newest matches and the other four pages on saved backlog progress. New issues in that first page arrive on the next successful sweep; older newly matching issues outside it still wait for the scan to reach them. Missing connections/accounts, failed reads and unready projects retain visible errors while other projects continue; recovery clears errors with readable activity. Later source changes or deletion never rewrite tasks.

Readiness is checked before external reads. Explicit account sessions discover once per sweep or paginated option list. Settings conflicts are reported as skipped, and project statuses appear in dashboard snapshots. Imports and manual task requests share the transaction queue helper.

The editor caches account options and states and loads only the chosen project's teams. CLI team/project/user lists follow cursors up to five pages and 500 records, refusing failed later pages, cycles and incomplete lists instead of showing partial choices. Full bare pages without pagination are refused. Project-team reads refuse incomplete results beyond 50 teams. IDs use shared core validation.

Tests cover realistic and oversized descriptions, rules/argv, pagination failure, atomic/concurrent receipts, readiness, removed connections/accounts, stale reads, 751-issue progress, unchanged writes, activity visibility, scoped cached options and board-link stacking. Generated assets are rebuilt from merged source. CA-52 remains the queued follow-up for editing arbitrary task issue/project links. Source writes, global enrollment, webhooks, extra filters and assistant tools are out of scope.

Storage trade-off: bounded descriptions remained in task source records in the whole-state document so offline roles retained their original context. At the 8KiB limit, 50 imports could add roughly 400KiB to state writes and dashboard snapshots, even though the dashboard only displayed identifiers, titles and URLs. This kept persistence and context retrieval simple, but large backlogs would merit separating cold source context from the hot state document; this change did not introduce a second storage system.
